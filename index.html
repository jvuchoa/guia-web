Fundamentos de Aplicações Web

Guia de consulta para conceitos essenciais de desenvolvimento web, arquitetura, deploy e ferramentas de desenvolvimento.

1. Domínio da aplicação

O domínio da aplicação é o conjunto de conceitos, regras e informações do negócio que o sistema representa. Ele define o que a aplicação precisa fazer e quais regras deve respeitar.

Exemplo: em um sistema de agendamento, o domínio pode incluir clientes, profissionais, horários disponíveis, agendamentos e regras para cancelamento.

Para lembrar: domínio = regras e conceitos do negócio.

2. Momentos e partes de uma aplicação

Uma aplicação web costuma ter diferentes partes e ambientes.

Localhost

Localhost é o próprio computador onde a aplicação está sendo executada. É muito usado durante o desenvolvimento e os testes locais.

Client (cliente)

É a parte com a qual o usuário interage ou o dispositivo que faz as requisições ao servidor.

  • Front-end: interface visual da aplicação, como páginas, formulários, botões e telas.
  • Mobile: aplicativo desenvolvido para dispositivos móveis. Ele também pode consumir uma API de back-end.

Server (servidor / back-end)

É a parte que recebe requisições, executa regras de negócio, acessa dados e devolve respostas.

O back-end pode: - aplicar as regras de negócio; - servir e processar dados; - comunicar-se com outros back-ends e APIs; - integrar-se com ferramentas de IA; - acessar sistemas de banco de dados.

Cloud (nuvem)

É o uso de infraestrutura e serviços disponibilizados pela internet para executar, armazenar ou gerenciar aplicações.

Exemplos de plataformas e serviços citados no mapa: - AWS (Amazon Web Services) - GCP (Google Cloud Platform) - Oracle Cloud - Vercel - Railway

Deploy

Deploy é o processo de disponibilizar uma versão da aplicação em um ambiente, por exemplo, para que usuários possam acessá-la pela internet. Dependendo do projeto, pode envolver publicar o front-end, o back-end e configurar banco de dados e variáveis de ambiente.

Fluxo simplificado: desenvolver localmente → testar → publicar (deploy) → usuários acessam.

3. Tipos de aplicações e arquitetura

Aplicações CRUD

CRUD representa quatro operações básicas de manipulação de dados:

Sigla Termo em inglês Significado Exemplo
C Create Criar Cadastrar um cliente
R Read Ler/consultar Listar clientes
U Update Atualizar Alterar os dados de um cliente
D Delete Excluir Remover um cadastro

Essas operações são comuns em sistemas de cadastro, estoque, agendamento e administração.

Web services

Um web service é uma forma de um sistema disponibilizar funcionalidades ou dados para que outro sistema se comunique com ele por uma rede, normalmente usando padrões e protocolos definidos.

Exemplo: o front-end envia uma requisição HTTP para uma API; o servidor processa a solicitação e devolve uma resposta em JSON.

Importante: web service descreve uma forma de comunicação entre sistemas. Não é, por si só, um estilo de arquitetura como microsserviços.

Microsserviços

Em uma arquitetura de microsserviços, a aplicação é dividida em serviços menores, com responsabilidades específicas. Esses serviços podem ser desenvolvidos, implantados e escalados de forma relativamente independente.

Exemplo em um e-commerce: - serviço de usuários; - serviço de produtos; - serviço de pedidos; - serviço de pagamentos.

Os serviços precisam se comunicar e a arquitetura exige atenção à rede, segurança, monitoramento, consistência de dados e implantação.

Vantagem possível: cada serviço pode evoluir ou escalar de acordo com sua necessidade.

Custo possível: há mais complexidade operacional e de comunicação entre componentes.

Monólito

Em uma arquitetura monolítica, as principais funcionalidades do sistema ficam reunidas em uma única aplicação implantável. Isso não significa necessariamente que o código seja desorganizado: um monólito pode ter módulos e uma boa separação de responsabilidades.

Vantagens comuns: simplicidade inicial, desenvolvimento e implantação mais diretos.

Desafios possíveis: com o crescimento do sistema, mudanças e escalabilidade podem ficar mais difíceis se os módulos estiverem muito acoplados.

Comparação rápida

Conceito O que descreve? Exemplo
CRUD Operações sobre dados Criar, consultar, atualizar e excluir produtos
Web service Comunicação entre sistemas Uma API HTTP que retorna dados em JSON
Microsserviços Organização da aplicação em serviços menores Serviços separados para pedidos e pagamentos
Monólito Aplicação reunida em uma unidade principal de implantação Uma API que contém módulos de produtos, clientes e pedidos

Como os conceitos se relacionam: um monólito ou um microsserviço pode expor web services. CRUD pode existir dentro de ambos. Portanto, esses termos não são alternativas equivalentes: cada um descreve um aspecto diferente.

4. APIs: conceitos básicos

O que é uma API

API (Application Programming Interface) é uma interface que define como um software pode pedir dados ou serviços a outro, sem precisar conhecer a implementação interna. Funciona como um contrato: o que pode ser solicitado, em que formato e o que será devolvido.

Analogia: o cardápio e o garçom de um restaurante. Você pede pelo cardápio (contrato) e recebe o prato, sem saber como a cozinha funciona.

Exemplo: uma aplicação de agendamento consulta uma API para listar horários disponíveis; um site de compras consulta uma API de CEP para preencher o endereço.

Neste guia, o foco é a Web API: aquela acessada pela rede por meio do protocolo HTTP.

HTTP: request e response

O HTTP segue o modelo requisição–resposta: o cliente envia uma request e o servidor devolve uma response. Cada par é independente (o protocolo é stateless, isto é, não guarda estado entre requisições).

ElementoRequest (cliente → servidor)Response (servidor → cliente)
Linha inicialMétodo + URL (ex.: GET /clientes/7)Código de status (ex.: 200 OK)
Headers (cabeçalhos)Metadados: Content-Type, Accept, AuthorizationMetadados: Content-Type, Location
Body (corpo)Opcional; dados enviados (ex.: JSON em um POST)Opcional; dados devolvidos (ex.: JSON)

Exemplo de request

POST /api/agendamentos HTTP/1.1
Host: api.exemplo.com
Content-Type: application/json
Authorization: Bearer SEU_TOKEN

{"clienteId": 7, "horario": "2026-11-03T14:00"}

Exemplo de response

HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/agendamentos/42

{"id": 42, "clienteId": 7, "horario": "2026-11-03T14:00", "status": "AGENDADO"}

Métodos HTTP

O método indica a intenção da requisição e se relaciona com as operações do CRUD.

MétodoFinalidadeCRUDExemplo
GETConsultar um recurso ou uma listaReadGET /clientes
POSTCriar um novo recursoCreatePOST /clientes
PUTSubstituir um recurso por completoUpdatePUT /clientes/7
PATCHAlterar parte de um recursoUpdatePATCH /clientes/7

Detalhe importante: GET não deve alterar dados no servidor. GET, PUT e DELETE são idempotentes (repetir a mesma requisição produz o mesmo estado final); POST normalmente não é.

Códigos de status

FaixaSignificadoExemplos comuns
1xxInformativo—
2xxSucesso200 OK, 201 Created, 204 No Content
3xxRedirecionamento301 Moved Permanently, 304 Not Modified
4xxErro do cliente400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict

Para lembrar: 4xx = o problema está na requisição; 5xx = o problema está no servidor.

API REST

REST (Representational State Transfer) é um estilo arquitetural para sistemas distribuídos, descrito por Roy Fielding em sua tese de doutorado (2000). Não é um protocolo nem um padrão formal: é um conjunto de restrições. Uma API REST é uma Web API construída segundo essas restrições.

  • Cliente–servidor: responsabilidades separadas.
  • Stateless: cada requisição carrega todas as informações necessárias; o servidor não guarda sessão do cliente entre chamadas.
  • Cacheável: respostas podem indicar se podem ser reutilizadas.
  • Interface uniforme: recursos identificados por URLs, manipulados por meio de representações (como JSON) e métodos HTTP com semântica padronizada.
  • Sistema em camadas: o cliente não precisa saber se fala direto com o servidor final ou com intermediários (proxy, gateway).
  • Código sob demanda (opcional): o servidor pode enviar código executável ao cliente.

Recursos e URLs

Em REST, a URL identifica um recurso (um substantivo), e o método HTTP indica a ação.

EvitePrefira
GET /buscarClientesGET /clientes
POST /criarClientePOST /clientes
POST /excluirCliente?id=7DELETE /clientes/7

API RESTful

“RESTful” é o adjetivo para uma API que de fato segue os princípios REST. No uso cotidiano do mercado, API REST e API RESTful costumam ser tratadas como sinônimos. A distinção útil é conceitual: REST é o estilo; RESTful descreve uma implementação aderente a ele.

Uma forma comum de medir essa aderência é o Modelo de Maturidade de Richardson:

NívelCaracterística
0Um único endpoint, usado como túnel para chamadas (estilo RPC)
1Recursos: cada entidade tem sua própria URL
2Uso correto dos métodos HTTP e dos códigos de status
3Controles de hipermídia (HATEOAS): a resposta traz links para as próximas ações possíveis

Na prática, a maioria das APIs chamadas de “REST” permanece no nível 2. Pela definição estrita de Fielding, a hipermídia (nível 3) é parte essencial do REST.

Para lembrar: API = contrato de comunicação; Web API = esse contrato sobre HTTP; REST = estilo arquitetural; RESTful = API que o segue de verdade. Request = pedido (método, URL, headers, body); response = resposta (status, headers, body).

5. Repositório e controle de versão

Um repositório é o local onde o código e, normalmente, o histórico de alterações de um projeto são armazenados e organizados.

Repositório remoto

Fica em uma plataforma online, permitindo compartilhar código, colaborar e manter uma cópia acessível pela equipe.

Exemplos de plataformas: GitHub, GitLab e Bitbucket.

Repositório monorepo

Em um monorepo, vários projetos ou partes de um sistema ficam no mesmo repositório. Por exemplo, o front-end e o back-end podem estar juntos.

Repositórios separados

O front-end e o back-end ficam em repositórios diferentes. Isso pode facilitar permissões, ciclos de publicação e organização de equipes independentes.

Importante: monorepo não significa necessariamente monólito. Monorepo é uma estratégia de organização do código; monólito e microsserviços descrevem a arquitetura da aplicação.

Git

O Git é um sistema de controle de versão que registra mudanças nos arquivos ao longo do tempo. Ele permite comparar versões, criar branches e integrar alterações.

6. CI/CD

CI/CD é um conjunto de práticas para automatizar partes do processo de integração, teste, entrega e implantação de software.

CI — Continuous Integration (Integração Contínua)

É a prática de integrar mudanças de código frequentemente e executar verificações automatizadas, como compilação e testes.

Objetivo: detectar problemas cedo e manter o código integrado em boas condições.

CD — Continuous Delivery (Entrega Contínua)

As alterações aprovadas pelos testes ficam preparadas para serem publicadas. A implantação em produção pode ainda exigir uma aprovação ou ação manual.

CD — Continuous Deployment (Implantação Contínua)

As alterações que passam pelas verificações automatizadas são implantadas em produção automaticamente, sem uma aprovação manual para cada publicação.

Diferença essencial: - Continuous Delivery: deixa a versão pronta para publicação. - Continuous Deployment: publica automaticamente quando todos os critérios são atendidos.

CI/CD não elimina a necessidade de testes, monitoramento ou boas práticas de segurança.

7. Frameworks x bibliotecas

Biblioteca

Uma biblioteca é um conjunto de funções e ferramentas que você chama quando precisa resolver uma tarefa específica. Em geral, o desenvolvedor controla mais diretamente o fluxo da aplicação.

Exemplo: usar uma biblioteca para validar dados, manipular datas ou fazer requisições HTTP.

Framework

Um framework fornece uma estrutura e convenções para organizar e construir uma aplicação. Ele define parte do fluxo de execução e indica como os componentes devem se encaixar.

Uma ideia útil para diferenciar: - Biblioteca: você chama a biblioteca quando precisa dela. - Framework: a aplicação segue a estrutura do framework, que pode chamar o seu código em momentos determinados.

Exemplos citados no mapa

  • Node.js + Express: Express é um framework web para Node.js.
  • Ruby on Rails: framework web para Ruby.
  • Java + Spring Boot: Spring Boot facilita a criação e configuração de aplicações baseadas no ecossistema Spring.
  • .NET + ASP.NET Core: tecnologias usadas para criar aplicações e serviços web no ecossistema .NET.

Observação: Node.js é um ambiente de execução JavaScript, enquanto Express é um framework; Java é uma linguagem, enquanto Spring Boot é uma ferramenta do ecossistema Spring. Não são categorias equivalentes.

8. Livros recomendados

Os três livros que aparecem no mapa:

  1. Microsserviços Prontos para a Produção — referência para estudar decisões, práticas e desafios de microsserviços em ambientes reais.
  2. Estruturas de Dados e Algoritmos com JavaScript — material para compreender estruturas de dados e algoritmos usando JavaScript.
  3. APIs: A arte de criar e consumir APIs — referência para entender o desenho, a criação e o consumo de APIs.

Use os livros de acordo com a etapa de estudo: fundamentos de algoritmos e estruturas de dados; comunicação por APIs; depois, arquitetura distribuída e microsserviços.

9. Resumo para revisão

  • Domínio: regras e conceitos do negócio que a aplicação representa.
  • Front-end: interface e interação com o usuário.
  • Back-end: regras de negócio, processamento e acesso a dados.
  • Localhost: aplicação executando localmente no próprio computador.
  • Cloud: infraestrutura e serviços acessíveis pela internet.
  • Deploy: publicação de uma versão da aplicação em um ambiente.
  • CRUD: criar, ler, atualizar e excluir dados.
  • Web service: mecanismo/serviço de comunicação entre sistemas.
  • Microsserviços: arquitetura dividida em serviços menores com responsabilidades específicas.
  • Monólito: aplicação implantada como uma unidade principal.
  • Repositório: local de armazenamento e histórico do código.
  • Monorepo: vários projetos ou partes no mesmo repositório.
  • Git: controle de versão.
  • CI: integração frequente com verificações automatizadas.
  • Continuous Delivery: versão pronta para publicação.
  • Continuous Deployment: publicação automática após passar pelas verificações.
  • Biblioteca: conjunto de funcionalidades que o código utiliza.
  • Framework: estrutura e convenções para desenvolver uma aplicação.
